# 架构设计详细规范（开发之前 · 阶段 2）

> 位置：原型确认之后、迭代开发之前。业界共识：架构在开发前（BMAD 的 analyst→PM→architect→dev→QA 链路同序）。
> 核心思想（吸收 BMAD "architecture spine"）：**只固定不变量，不画大而全**——判断某项要不要固定，就问"两个模块独立开发会不会做出不兼容的选择？"会且是真实权衡才固定，不会就留给代码自己演化。

## 三项必做

### 1. 技术选型

原则：**选最主流的不选最先进的**——主流技术训练语料最多，AI 生成质量最高、踩坑最少。

| 产品形态 | 推荐栈 | 说明 |
|---|---|---|
| Web App（首选） | Vite + React/Vue + Tailwind | 生态最大，改完即见 |
| 微信小程序 | 原生小程序 / uni-app | 视目标平台而定 |
| 桌面/移动原生 | 仅在确有必要时 | 原型期一律用 Web 替代验证 |

**数据先行**：第一版数据全放 localStorage / IndexedDB，界面跑通后再接云端——避免"界面没确认就先建后端"。

### 2. 最小架构设计（防止两个极端）

既防"不设计"（模块边界混乱、后期返工），也防"过度设计"（产品没用户先画微服务）。只固定三类不变量：

- **数据模型**：实体、字段、类型、关系（金额一律整数分存储）。界面推翻很便宜，数据模型最难改——它随数据积累固化。产出 `docs/数据模型.md`（模板：`assets/templates/数据模型模板.md`）；
- **模块划分**：本项目拆几个模块/目录，各自职责一句话。小项目可能就一个模块——那也是一条决策；
- **模块间契约**（仅多模块时）：模块 A 调模块 B 走什么接口/数据结构。单模块项目跳过。

### 3. 架构决策记录（AD）

每条架构决策编号记录（AD-1、AD-2…），格式：**选了什么 / 放弃了什么 / 什么条件下重新评估**。产出 `docs/架构决策.md`（模板：`assets/templates/架构决策模板.md`）。决策带编号的用处：下游开发引用（"按 AD-2 用 localStorage"），半年后还能查到当时的取舍。

## 与相邻阶段的衔接

- **上游（原型）**：继承原型已定的信息架构与页面清单，不重新讨论；
- **下游（开发）**：任务拆解以架构决策为依据；开发中发现架构不变量被现实打破，走总纪律的**偏离协议**（停下报告，更新 AD 后再动）。

## 项目初始化清单

- [ ] 脚手架建项目（如 `npm create vite@latest`）
- [ ] `git init` + 首笔 commit（从此每完成一步就 commit）
- [ ] 原型拆组件搬进项目（原型是 UI 骨架不是废物）
- [ ] `npm run dev` 跑通，浏览器确认工程可打开
