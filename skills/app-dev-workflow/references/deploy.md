# 部署决策详细规范（阶段 5 · 本地测试通过后）

> 这一步决定的是"**要不要后端、怎么上线**"——部署级决策，不是软件架构（架构已在阶段 2 完成）。
> 原则：**按需求触发，不按想象触发**。个人项目常见的浪费是产品还没用户就先上后端。

## 第一步：真的需要后端吗？（五条触发条件，任一命中才上）

- [ ] 多用户/账号体系（登录、数据隔离）
- [ ] 多端同步（手机 + 电脑同一份数据）
- [ ] 数据需要人与人共享（评论、协作、社交）
- [ ] 有不能暴露给客户端的东西（支付、密钥、防作弊）
- [ ] 数据量或计算量超出浏览器能力

**零命中 → 不上后端**：静态托管 + localStorage/IndexedDB 就是终态（很多工具类应用如此）。

## 第二步：后端形态三选一（从轻往重，能不往下走就不走）

| 形态 | 适合 | 特点 |
|---|---|---|
| 静态 + BaaS（CloudBase / Supabase 类） | 有账号和数据存储，业务逻辑简单 | 前端直连托管数据库，几乎零后端代码，权限用平台安全规则 |
| Serverless 云函数 + 托管数据库 | 少量必须服务端执行的业务逻辑 | 免运维、按量计费，接口粒度可粗 |
| 前后端分离（独立 API + 数据库） | 复杂业务、团队协作、高并发 | 最灵活也最贵：要设计 API、管部署运维 |

个人项目 90% 的答案在前两行。

## 第三步：职责划分与 API 契约（仅分离形态需要）

- **前端**：展示、交互、输入校验——前端校验是"为了体验"；
- **后端**：业务规则、数据校验、鉴权、持久化——**后端永远不信任前端**发来的任何数据；
- **API 设计**：资源化命名（`/api/v1/records` 而非 `/api/getRecordList`）；**先写一页 API 契约**（路径/方法/入参/出参/错误码）再开发，契约是前后端（及 AI 分头开发两端）的对齐物；版本化从 `/v1/` 开始。

## 上线路径（决策后）

- 零后端：构建产物 → 静态托管（起步最省）→ 域名（可选）；
- 有后端：数据层从 localStorage 迁移云端 → 后端部署 → 前端切环境变量 → 联调走查核心流程再发布。
