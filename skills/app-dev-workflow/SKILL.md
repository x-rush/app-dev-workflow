# 应用开发工作流

六阶段流水线：**想清楚 → 画出来 → 定地基 → 小步跑 → 测到位 → 定架构**。

## 总纪律（每个阶段都适用）

1. **一次只推进一个阶段**。每阶段结束：向用户展示产出 + 对照过关标准汇报证据，由用户三选一确认——**通过**（进入下一阶段）/ **修改**（指出问题，改完重新汇报）/ **打回**（回到上一阶段）。
2. **生图前置确认（默认必做）**：AI 生图成本不可逆、审美高度主观，任何生图（界面概念图、插画、图标、氛围图）前先与用户确认三项——**风格方向、内容预期**（图里会画什么/不画什么）**、数量与用途**；项目已有用户确认过的风格规范（如 `docs/art-style-guide.md`）时，风格项视为已确认。概念图是草稿不是原型（乱码文字属正常，只看方向）。
3. **能免费验证的别花钱**：布局、文案、交互全部在 HTML 原型里验证；生图只用于看方向（~$0.07/张，方向犹豫时才花）和当素材（界面真需要时才生成）。
4. **设计系统先行**：写界面前必须先过情绪板/设计系统——色值、字体、间距有出处，禁止跳过直接堆界面。
5. **证据反幻觉**：过关汇报必须来自实际执行（服务真跑过、界面真点过、测试真跑过），禁止用"应该没问题"式推断代替证据；不确定就当场验证。
6. **偏离协议**：执行中发现需要超出当前任务范围的改动（改需求、动其他模块、引新依赖），停下报告并给选项，获批后再动——禁止顺手就改。
7. **文档即接口**：阶段 N+1 以阶段 N 产出的 `docs/` 文件为唯一事实来源，从文件读取而非从对话记忆推断；发现文件与实际不符，先更新文件再继续。

## 规则分层（从低到高，高层覆盖低层）

1. **skill 默认**：本文件与 references/，全流程通用最佳实践；
2. **个人覆盖**：`<skill>/MY-RULES.md`——本机长期规则（确认强度、预算上限等），存在则触发时必读；
3. **项目覆盖**：项目根 `docs/workflow-rules.md`——该项目特有需求与偏好，优先级最高。

三层冲突时以高层为准；项目结束把可复用的项目规则沉淀回个人层。

## 触发后的第一步

1. 判断用户当前所处阶段：全新想法从阶段 0 开始；已有明确需求和参考可压缩阶段 0；已有原型从阶段 2 开始；已有代码从阶段 3 续（先跑起来看现状再列任务）。
2. **只读当前阶段的 references/ 文件**（其余阶段的不加载——上下文是成本，用不到的内容不进脑）。
3. 向用户展示本次的阶段计划（要走到哪、每步产出什么），确认后开工。

## 阶段 0 · 需求讨论（想清楚）

**动作**：一句话产品定义（给谁用/解决什么问题/凭什么用你）；3~5 条核心用户流程（作为__我想要__以便__）；极简流程图（打开→完成核心任务的路径）；**暂不做清单**（MVP 范围外 explicitly 列出）。

**协作姿势**：此阶段不写代码。AI 扮演"追问者"，把需求模糊点逐个问出来（谁登录？数据存哪？没网怎么办？）。

**产出**：`docs/需求.md`——用 `assets/templates/需求文档模板.md` 生成后填实。

**过关标准**：用户能 30 秒讲清产品；页面清单 ≤ 6。

## 阶段 1 · 原型（画出来）

**先读 `references/prototype.md`（情绪板做法、生图规范、成本表）。**

流程：情绪板定调（关键词/具体色值/字体气质，纯 CSS 拼板，可出 2~3 个方向让用户挑）→ 按板写 HTML 可交互原型（真实中文文案、可点击、响应式）→ 浏览器走查。方向犹豫时可加生图界面概念图（遵守生图前置确认）。

**过关标准**：每条核心用户流程在原型里完整走通，没有"这里到时候再说"。

## 阶段 2 · 技术选型与初始化（定地基）

**先读 `references/dev.md` 的选型与初始化节。**

要点：选最主流不选最先进（Web 默认 Vite + React/Vue + Tailwind）；**数据先行**——第一版数据全放 localStorage/IndexedDB，界面跑通再接云端；原型代码搬进项目当 UI 骨架；`git init` 且从此每步 commit。

**唯一前置的架构动作 · 数据模型设计**：`docs/数据模型.md`（用 `assets/templates/数据模型模板.md` 生成）——实体、字段、类型、关系。界面推翻很便宜，数据模型最难改。

**过关标准**：dev 服务器跑通；git 首笔提交。

## 阶段 3 · 迭代开发（小步跑）

**先读 `references/dev.md` 的开发纪律节。**

任务拆解到"半天一个"粒度，每任务走循环：**改 → 本地看 → 亲手点 → git commit**。

**AI 协作纪律**：一次只做一个任务，验证后再接下一个；用户反馈要具体（报错原文/期望vs实际）；AI 大改前先 commit；AI 每完成一个功能必须自测（启动本地服务、截图或自动点击验证）后才算交付。

**过关标准**：核心用户流程在本地完整走通（可以丑、数据可以是假的）。

## 阶段 4 · 本地测试（测到位）

**先读 `references/dev.md` 的测试节。**

四层递进：① 手动走查（把需求文档的用户流程逐条变检查项 + 空状态 + 异常输入 + 手机宽度）；② 基础自检（Console 零报错、无 404、键盘可达）；③ 自动化（关键逻辑单元测试、核心流程 E2E——可用浏览器自动化代跑）；④ **AI 敌对测试**（乱输入、快速连点、中途刷新、非法路由，专找用户的操作习惯发现不了的问题）。

**产出**：`docs/测试清单.md`（用 `assets/templates/测试清单模板.md` 生成，逐条打勾留痕）。

**过关标准**：清单全绿；一个没参与开发的人无需口头指导能完成核心任务。

## 阶段 5 · 前后端架构决策（本地测试通过后）

**先读 `references/architecture.md`。**

这是流程中正式的架构讨论点。三步：① 五条触发条件检查（多用户/多端同步/数据共享/敏感逻辑/数据量），零命中则不上后端；② 后端形态从轻往重三选一（静态+BaaS → Serverless → 前后端分离）；③ 仅分离形态需做职责划分与 API 契约（先写一页契约再开发）。

**产出**：`docs/架构决策.md`（用 `assets/templates/架构决策模板.md` 生成：选了什么/为什么/放弃了什么/何时机重评）。

## 阶段之后（提示用户但不自动展开）

数据层迁移云端 → 部署（静态托管起步最省）→ 真实用户反馈 → 回到阶段 0 迭代下一版。上线不是终点，是下一轮需求的起点。
