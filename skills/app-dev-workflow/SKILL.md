# 应用开发工作流

六阶段流水线：**想清楚 → 画出来 → 定架构 → 小步跑 → 测到位 → 稳上线**。

## 总纪律（每个阶段都适用）

1. **阶段门禁分两种（讨论前置，长跑交付）**：需求与原型（阶段 0→1→2 入口）必须用户三选一确认——**通过** / **修改**（改完重新汇报）/ **打回**——确认前不前进，用户的沉默与"好了"不构成通过；原型通过后自动进入**长跑模式**：阶段 2~5 由 AI 按过关标准证据自检、自主推进，不再逐步请示（边界见「推进模式」节）。
2. **生图前置确认（默认必做）**：AI 生图成本不可逆、审美高度主观，任何生图（界面概念图、插画、图标、氛围图）前先与用户确认三项——**风格方向、内容预期**（图里会画什么/不画什么）**、数量与用途**；项目已有用户确认过的风格规范（如 `docs/art-style-guide.md`）时，风格项视为已确认。概念图是草稿不是原型（乱码文字属正常，只看方向）。
3. **能免费验证的别花钱**：布局、文案、交互全部在 HTML 原型里验证；生图只用于看方向（~$0.07/张，方向犹豫时才花）和当素材（界面真需要时才生成）。
4. **设计系统先行**：写界面前必须先过情绪板/设计系统——色值、字体、间距有出处，禁止跳过直接堆界面。
5. **证据反幻觉**。铁律：**跳过任何验证步骤 = 撒谎，不是验证**。过关汇报必须来自本会话的实际执行——证据先于声明，对照下表：

   | 声明 | 需要的证据 | 不算证据 |
   |---|---|---|
   | "功能完成" | 本会话启动服务、亲手点过该功能 | 代码写完了、"应该可以" |
   | "测试通过" | 本次运行的输出（0 failures） | 上次跑过、日志看起来正常 |
   | "修好了" | 原症状复现路径已验证消失 | 改了代码、推断已修 |
   | "界面没问题" | 截图/自动走查的实际输出 | 布局代码看起来对 |

   出现"应该/大概/看起来"措辞时：停下，当场跑出证据再开口。
6. **偏离协议与外科手术式修改**：每一行改动都应能追溯到用户的请求。发现需要超出当前任务范围的改动（改需求、动其他模块、引新依赖），停下报告并给选项，获批后再动；不顺手"改进"相邻代码/注释/格式；发现无关死代码提一句但别删；自己的改动造成的孤儿代码（失效 import/变量/函数）要清理，预先存在的不动。**简单性纪律**：没要求的功能不做、单次使用的代码不抽象、没要求的灵活性不留；写完自问"高级工程师会说这过度复杂吗？"——会就重写。
7. **文档即接口**：阶段 N+1 以阶段 N 产出的 `docs/` 文件为唯一事实来源，从文件读取而非从对话记忆推断；发现文件与实际不符，先更新文件再继续。

## Red Flags（出现这些念头 = 正在合理化，停下来）

| 念头 | 现实 |
|---|---|
| "这只是个小功能，不用走阶段" | 纪律不分大小，小功能也要过关标准 |
| "需求大体清楚了，边做边问" | 阶段 0 的意义就是问清；边做边问 = 返工 |
| "原型先随便写写，后面再调" | 没有情绪板的"随便"就是 AI 味的开始 |
| "测试通过了" | 哪条命令的输出？本会话跑的吗？没证据 = 没通过 |
| "这个改动顺手也做了吧" | 偏离协议；每行改动都要能追溯到请求 |
| "再加点灵活性以后好用" | 简单性纪律：没要求的投机不做 |
| "架构以后再说" | 阶段 2 必须定最小架构（数据模型/模块划分/AD） |
| "我记得文档里说…" | 从文件读，不从记忆推断（文档即接口） |

## 规则分层（从低到高，高层覆盖低层）

1. **skill 默认**：本文件与 references/，全流程通用最佳实践；
2. **个人覆盖**：`<skill>/MY-RULES.md`——本机长期规则（确认强度、预算上限等），存在则触发时必读；
3. **项目覆盖**：项目根 `docs/workflow-rules.md`——该项目特有需求与偏好，优先级最高。

三层冲突时以高层为准；项目结束把可复用的项目规则沉淀回个人层。

## 触发后的第一步

1. 判断用户当前所处阶段：全新想法从阶段 0 开始；已有明确需求和参考可压缩阶段 0；已有原型从阶段 2 开始；已有代码从阶段 3 续（先跑起来看现状再列任务）。
2. **只读当前阶段的 references/ 文件**（其余阶段的不加载——上下文是成本，用不到的内容不进脑）。
3. 向用户展示本次的阶段计划（要走到哪、每步产出什么），确认后开工。

## 推进模式：讨论前置，长跑交付

**默认 `gate: confirm-prototype`**：阶段 0~1 人工确认（需求、原型——错误传播最贵的两处，讨论全部前置到此）；原型通过即进入**长跑**：阶段 2~5 按各阶段过关标准自主推进，判定依据是客观证据（服务真跑通、测试清单全绿、决策已成文留痕），而非人工点头。

**架构快照确认（阶段 2 出口，唯一追加的人工关口）**：架构是仅次于需求的错误传播点，长跑经过阶段 2 出口时亮出 AD 决策表做 30 秒快照确认——用户无异议或未回应即继续跑，**不阻塞**；有异议按"修改"处理。确认点跟着错误传播成本走，除此之外不再增设人工关口。

**长跑安全阀**（遇到即停，回来找用户，其余情况自主裁定）：
1. 偏离协议触发：需要计划外的改动（改需求 / 动其他模块 / 引新依赖）；
2. 需要生图（前置确认三件套：风格 / 内容预期 / 数量）；
3. 生图预算超支；
4. 需求出现歧义或矛盾，无法自行裁定；
5. 需要外部账号、凭证或付费资源；
6. **连续失败**：同一任务连续 3 次验证未通过即停（重复失败 = 假设错了，硬试是烧钱），带三次失败的完整记录回来报告。

**心跳播报**：每完成一个阶段，在会话留一条带证据的一行简报（如"[阶段3] 核心流程跑通 · 测试输出 0 failures · commit a1b2c3"）——只记录、不等待，用户随时回看进度。

**长跑产出与交付验收**：每阶段证据落 `docs/`（架构决策、测试清单等）；跑完一次性提交**交付报告**——各阶段证据汇总 + 测试结果 + 已知问题清单——用户验收通过项目才算完结；不通过的部分按"修改"处理。

**模式可覆盖**（写入项目 `docs/workflow-rules.md`）：`gate: all-manual`（每阶段都人工确认，适合高风险项目）；`gate: auto-after-requirements`（连原型确认也省，风险自担）。

## 阶段 0 · 需求讨论（想清楚）

**动作**：一句话产品定义（给谁用/解决什么问题/凭什么用你）；3~5 条核心用户流程（作为__我想要__以便__）；极简流程图（打开→完成核心任务的路径）；**暂不做清单**（MVP 范围外 explicitly 列出）。

**协作姿势**：此阶段不写代码。AI 扮演"追问者"，把需求模糊点逐个问出来（谁登录？数据存哪？没网怎么办？）。

**产出**：`docs/需求.md`——用 `assets/templates/需求文档模板.md` 生成后填实。

**过关标准**：用户能 30 秒讲清产品；页面清单 ≤ 6。

## 阶段 1 · 原型（画出来）

**先读 `references/prototype.md`（情绪板做法、AI 味自检清单、生图规范、成本表）。**

流程：情绪板定调（关键词/具体色值/字体气质，纯 CSS 拼板，可出 2~3 个方向让用户挑）→ 按板写 HTML 可交互原型（真实中文文案、可点击、响应式）→ 浏览器走查。方向犹豫时可加生图界面概念图（遵守生图前置确认）。

**过关标准**：每条核心用户流程在原型里完整走通，没有"这里到时候再说"。

## 阶段 2 · 架构与初始化（定架构）

**先读 `references/architecture.md`（开发前架构设计 · 最小架构原则）。**

三件事：

1. **技术选型**：选最主流不选最先进（Web 默认 Vite + React/Vue + Tailwind）；**数据先行**——第一版数据全放 localStorage/IndexedDB，界面跑通再接云端；
2. **最小架构设计**：只固定"改起来贵"的不变量——数据模型（实体/字段/关系，金额用整数分）、模块划分、模块间接口契约（多模块时）。判断标准：两个模块独立开发会不会做出不兼容的选择？会才固定，不会就不写，禁止画大而全架构图。产出 `docs/数据模型.md` + `docs/架构决策.md`（AD 编号决策记录）；
3. **项目初始化**：`git init`（从此每步 commit）、原型代码搬进项目当 UI 骨架、`npm run dev` 跑通。

**过关标准**：dev 服务器跑通；git 首笔提交；数据模型与架构决策文档完成。

## 阶段 3 · 迭代开发（小步跑）

**先读 `references/dev.md` 的开发纪律节。**

任务拆解到"半天一个"粒度，每任务走循环：**改 → 本地看 → 亲手点 → git commit**。

**AI 协作纪律**：一次只做一个任务，验证后再接下一个；用户反馈要具体（报错原文/期望vs实际）；AI 大改前先 commit；AI 每完成一个功能必须自测（启动本地服务、截图或自动点击验证）后才算交付。

**过关标准**：核心用户流程在本地完整走通（可以丑、数据可以是假的）。

## 阶段 4 · 本地测试（测到位）

**先读 `references/dev.md` 的测试节。**

四层递进：① 手动走查（把需求文档的用户流程逐条变检查项 + 空状态 + 异常输入 + 手机宽度）；② 基础自检（Console 零报错、无 404、键盘可达）；③ 自动化（关键逻辑单元测试、核心流程 E2E——可用浏览器自动化代跑）；④ **AI 敌对测试**（乱输入、快速连点、中途刷新、非法路由，专找用户的操作习惯发现不了的问题）。

**产出**：`docs/测试清单.md`（用 `assets/templates/测试清单模板.md` 生成，逐条打勾留痕）。

**过关标准**：清单全绿；一个没参与开发的人无需口头指导能完成核心任务。

## 阶段 5 · 部署决策（稳上线）

**先读 `references/deploy.md`。**

本地测试通过后决定"要不要后端、怎么上线"——这是**部署级决策**，按需求触发不按想象触发（防过度架构设计）：① 五条触发条件检查（多用户/多端同步/数据共享/敏感逻辑/数据量），零命中则不上后端；② 后端形态从轻往重三选一（静态+BaaS → Serverless → 前后端分离）；③ 仅分离形态做职责划分与 API 契约（先写一页契约再开发后端）。

**产出**：`docs/架构决策.md` 增补部署节（选了什么/为什么/放弃了什么/何时机重评）。

**过关标准**：部署形态已决策并记录；上线动作明确（静态托管起步最省）。

## 阶段之后（提示用户但不自动展开）

数据层迁移云端（若部署决策需要）→ 执行上线 → 真实用户反馈 → 回到阶段 0 迭代下一版。上线不是终点，是下一轮需求的起点。
